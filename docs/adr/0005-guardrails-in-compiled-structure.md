# Guardrail enforcement moves from runtime code to compiled structure in the gh-aw successor

devloop's guardrails are enforced in `forge/base.py` so no adapter can forget them, unit-tested, and denied at runtime by the agent CLI. The gh-aw migration plan replaces the Python orchestrator with compiled workflow sources, and that moves guardrail enforcement from runtime code to structure: agents run read-only and act only through gh-aw safe-outputs, whose per-workflow allow-lists (`add-labels.allowed` etc.) exclude merge/approve and every human-only label (`ai-*` triggers, `status/planned`). We accept this because the enforcement surface shrinks to compiled `.lock.yml` files that are reviewable diffs and re-compiled deliberately per repo (see `migration-plan.md`), whereas the denylist approach had to be re-implemented per engine.

What replaces the discarded guardrail unit tests is a compile-time drift check in the pipeline repo's CI: `gh aw list --stale` (fail if any lock file is out of sync with its source), plus assertions that `status/planned`, `ai-*` and `merge-pull-request` never appear in an agent workflow's safe-output allow-lists. This is a deliberate deviation from the obvious path of "just trust the platform defaults" — those defaults fail closed for command triggers (`on.roles`) but give no per-workflow allow-list enforcement for labels, so the drift check is the load-bearing replacement, not a nicety.

Consequence: the guardrail contract is now distributed across (1) `on.roles` fail-closed trigger gating, (2) per-workflow safe-output allow-lists, (3) the compile-drift CI check — instead of living in one module. The migration design's trust-model table (§2) is the map; drift in any layer is caught by (3).
